# ZIP 压缩性能修复

日期：2026-11-04。用户反馈 ZIP 慢于系统，使用本地 STEP 样本。样本为一个 49,414,158 字节（47.125 MiB）的 STEP 文件，无重解析点；源文件没有改写，输出与入口测试副本均在工程 artifacts 目录。

## 实测

| 项目 | 优化前 | 优化后 |
|---|---:|---:|
| 仅创建 ZIP，2 轮平均 | 4.948 秒 | 0.592 秒 |
| 应用快捷任务入口，含小窗口启动，2 轮 | 5.981 / 5.969 秒 | 2.490 / 1.488 秒 |
| ZIP 大小 | 11,251,158 字节 | 12,437,908 字节 |
| 标准模式进度回调次数，每轮 | 1,155 | 13–14 |

该样本仅压缩阶段耗时约降为原来的 1/8.36；含启动的实际应用入口耗时降为约 1/2.4–1/4。代价是压缩包增加约 10.55%，文件内容不变。所有性能测试压缩包均逐文件 SHA-256 校验。

应用入口测试在 artifacts 内复制相同源内容，通过 `--shell-request` 启动真实独立任务窗口，计时到最终 ZIP 提交，不是单纯测引擎。尚未精确计时资源管理器的 Windows「压缩到…」命令；.NET ZIP 仅作独立编码参考，不将其计时当作系统菜单实测。结果针对该文件、当前硬件及缓存条件，不代表其他文件类型均有相同加速。

## 修改

原实现所有 ZIP 均使用 7-Zip 的默认标准压缩，针对该 STEP 文本做了更多压缩搜索，CPU 时间接近总压缩时间；约 16 个逻辑处理器不代表单文件 Deflate 就能充分并行。本轮没有把慢速归因于线程未启用，也没有盲目增加线程数。

`ArchiveEngine.CreateAsync` 保留统一来源枚举、重解析点拒绝、重名检查、唯一临时文件与最终原子提交。未设置密码的 ZIP 分流至 `FastZipWriter`：

- 标准（level 4–6，界面为 5）：.NET `CompressionLevel.Optimal`。
- 更快（level 1–3，界面为 1）：`CompressionLevel.Fastest`，速度优先，压缩包可能更大。
- level 0：不压缩存储。
- 更小（level 7–9，界面为 9）、密码 ZIP 及全部 7z：继续调用原 7-Zip 引擎。

快速 ZIP 保持标准 Deflate/ZIP、UTF-8 名称、目录及空目录、文件时间/属性、128 KiB 流式缓冲和 ZIP64 支持，内存不随大文件内容整体增长。读取、预览、解压、校验仍使用 7-Zip。原生引擎进度跨托管层的通知限制为约每 50 ms 一次，取消仍在每次原生回调检查；快速 ZIP 每个复制块检查取消。

回归共 37 项通过，新增标准 ZIP 的默认 UTF-8 互通、更快/更小 ZIP 往返，以及取消时删除临时输出、禁止提交最终文件。原有 AES ZIP、7z 文件名加密、中文、空目录、冲突及路径安全检查继续通过。发布目录已更新，快捷 ZIP 请求与启动检查通过；没有恢复电脑界面控制或生成新的 UI 截图。

机器可读性能记录仅保存在本地，未将个人样本和路径上传仓库。复测工具：`tests/New7z.Performance`、`scripts/measure-shell-compression.ps1`。后者比较运行目录旧版与指定的新目录，应在替换运行目录之前执行，以免把两个新版当作前后版本比较。
