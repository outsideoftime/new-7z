# 批量解压性能修复

日期：2026-11-11。用户反馈 RAR 以及其他格式解压慢。问题位于公共解压流程，而非单个格式的解码器。

## 实测

| 样本 | 优化前，引擎解压 | 优化后，引擎解压 |
|---|---:|---:|
| 本地工程 RAR，5,858 个文件、494 个目录 | 194.482 秒 | 14.687 秒 |
| ZIP，512 个文件、32 MiB，2 轮平均 | 1.418 秒 | 0.626 秒 |
| 固实 7z，同上，2 轮平均 | 11.154 秒 | 0.615 秒 |
| TAR，同上，2 轮平均 | 3.896 秒 | 0.601 秒 |

RAR 原包 1,111,017,399 字节，解压文件共 1,353,999,949 字节。旧版和最终新版各完整测一次；开发期间另有两次中间版本验证。最终新版列举条目另耗时 0.101 秒。最终裁剪安装负载通过实际 `--shell-request` / `extract-named` 入口解压同一 RAR，从进程启动到最后文件提交耗时 **18.321 秒**，包括 WinUI 启动及任务准备。此入口测试读取工程目录中的测试副本，原始测试文件未被改写。

RAR 的 5,858 个文件和所有 ZIP / 7z / TAR 输出均逐文件计算 SHA-256，与旧版完整输出清单一致；哈希校验不计入解压计时。合成样本包括中文文件名、嵌套目录和空目录，512 个文件各为 64 KiB，相同的确定性随机数据适合复现固实块反复解码的问题。旧版与第一版批量实现做过两轮交替对比，最终减少元数据操作后的新版另测两轮。

这是当前机器和文件缓存条件下的本地测量，未控制冷缓存。Windows 自带解压约 10 秒为用户提供的结果，本次未在相同条件下测量系统菜单，不能据此宣称已追平系统，也不能把这些倍数推广到所有压缩包。

## 原因与修改

旧 `ArchiveEngine.ExtractAsync` 对每个文件单独调用 `NzExtract`。每次调用都会创建输入流、探测格式并重新解析压缩包；固实压缩包还会重复解码目标文件之前的内容。每个文件单独 `Task.Run` / `await`，从 UI 调用时还会反复切换线程；进度按文件开始和结束逐项入队。

新 `NzExtractBatch` 对一批选中条目只打开一次归档，按升序索引一次调用 7-Zip `Extract`，保留固实解码状态。预览仍使用单文件读取接口。普通解压、应用内选中条目解压和右键任务通过同一公共流程受益。

- 整次解压放在一个后台任务中，包括路径预检和目录准备。
- 所有路径和链接先预检；原生层重新检查索引、条目类型及大小上限。
- 每次只保持当前文件的输出流。逐文件写唯一临时文件，CRC 成功后关闭句柄并提交；损坏、取消或回调异常时保留已验证的输出并清理当前临时文件。
- 重名按实际提交顺序处理，保留重命名、跳过和替换策略，包括包内同名条目。
- 修改时间通过已打开的原生输出句柄设置，避免为每个文件重新打开一次。
- 进度通知限制为约每 50 ms 一次，取消仍在每次原生进度及条目回调检查。
- 路径各级组件使用一次文件属性查询检查重解析点，避免 `File.Exists` / `Directory.Exists` / `GetAttributes` 的重复查询；写入前和提交前仍重新检查。磁盘剩余空间使用保守预算，不足时刷新，实际写入错误仍由文件系统返回。
